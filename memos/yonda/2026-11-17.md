#PWA #設計判断
**Service Worker(SW)の作り方と、オフラインで再読み込みしたときの流れ**

## vite-plugin-pwa

- Vite のプラグイン 1 つで PWA にできる(SW の生成、事前キャッシュ一覧の作成、manifest など)
- 中身は Workbox(Google 製の SW 用ライブラリ)
- 作り方は 2 種類

| 方式                 | 内容                                                                         | 向いているもの                     |
| -------------------- | ---------------------------------------------------------------------------- | ---------------------------------- |
| generateSW           | 設定を書くだけで SW 全体を Workbox が自動生成する                            | 一般的な SPA(`index.html` が 1 枚) |
| injectManifest(採用) | SW は自分で書く(`src/sw.ts`)。プラグインは事前キャッシュの一覧を差し込むだけ | 動きをカスタムしたいとき           |

## SSR だと injectManifest(カスタム)が合う理由

問題は「オフラインのとき、どの HTML を返すか」。

|                       | SPA                                                                                                                 | 今回(SSR)                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| オフラインで返す HTML | ビルド時にできる `index.html` を事前キャッシュし、どの URL でもそれを返す(`navigateFallback: "index.html"` の 1 行) | ビルド時に HTML がない。HTML はリクエストごとにサーバーが作る                         |
| 必要な処理            | 設定だけ                                                                                                            | ① オンラインで開いたときの `/` の HTML を保存 ② オフラインならどの URL でもそれを返す |

- ② は generateSW の設定では素直に書けない(設定の中に関数を書くことになり読みにくい)→ `src/sw.ts` に十数行で直接書く方が単純
- `index.html` がないため、プラグインが本来自動でやる次の 2 つも自前(方式に関係なく必要)
  - SW の登録 → `__root.tsx` で `navigator.serviceWorker.register("/sw.js")`(本番のみ)
  - manifest の `<link>` → `__root.tsx` の head

## オフラインで再読み込みしたときの流れ

リダイレクトではない。URL はそのままで、返す HTML の中身だけが本棚のものになる。

例: オフラインで `/books/xxx` を再読み込み

| 順番 | 起きること                                                            | アドレスバー        | 画面              |
| ---- | --------------------------------------------------------------------- | ------------------- | ----------------- |
| 1    | ブラウザが `/books/xxx` の HTML を要求                                | `/books/xxx`        | —                 |
| 2    | SW が受け取る。ネットワークは失敗 → 保存しておいた `/` の HTML を返す | `/books/xxx` のまま | 一瞬、本棚の HTML |
| 3    | HTML に書かれた JS(事前キャッシュ済み)を読み込む                      | `/books/xxx`        | —                 |
| 4    | TanStack Router が URL を見て詳細画面をブラウザ側で描画               | `/books/xxx`        | 詳細画面          |

- 保存した `/` の HTML は「JS を読み込むための入れ物」。どの画面を出すかは JS(ルーター)が URL で決める
- 4 で「HTML は本棚、ルーターは詳細」の食い違い → React error #418(ハイドレーション不一致)。React が描画し直すので表示は正しい。オフライン時だけなので受け入れる
- `/` は SW が有効になった後の読み込みで初めて保存される(初回表示の直後にオフラインにすると返すものがない)

この処理が動くのは HTML を取りに行くときだけ。

| 操作                                               | HTML を取りに行くか         |
| -------------------------------------------------- | --------------------------- |
| アプリ内のリンク・タブで画面移動                   | 行かない(JS だけで切り替え) |
| 再読み込み・URL 直接・ホーム画面のアイコンから起動 | 行く → この処理が動く       |

## 残っている課題(手順 3 で対応)

- オフラインで詳細画面を開くとエラー。原因は HTML ではなくデータ(loader が `getBook` をサーバーに取りに行き失敗)
- TanStack Query の内容を IndexedDB に保存し、詳細は一覧のデータを使って表示する

## つまずいた点

- TanStack Start はクライアントと SSR を順にビルドし、プラグインは両方の設定を受け取る
- vite-plugin-pwa は最後に受け取った設定(SSR, `build.ssr: true`)を見て SW の生成を飛ばしていた
- `applyToEnvironment` では設定の受け取り(configResolved)は絞れなかった → `vite.config.ts` の `skipSsrConfig` で SSR の設定を渡さないようにした
