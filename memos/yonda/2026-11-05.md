#server #設計判断
**登録時の書誌情報(タイトル・著者・表紙)をどこで用意するか**

検索画面で「登録」を押したとき、保存するタイトル・著者・表紙 URL を誰が用意するかの判断。

前提: 検索はすでにサーバー経由(API キーをサーバーだけが持つため)

```
[クライアント] 検索ワードを送る
     ▼
[サーバー] Google Books API を呼ぶ → 必要な項目に変換・登録済み判定を付与
     ▼
[クライアント] 結果を表示 → 「登録」を押す
     ▼
[サーバー] 保存
```

画面に出ている値は、すでにサーバーが API から取得・整形したもの。

## 候補

| 案      | 登録時に送るもの              | サーバーの処理                                           | 得るもの                                | 失うもの                                                                                                   |
| ------- | ----------------------------- | -------------------------------------------------------- | --------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| A(採用) | ID + タイトル・著者・表紙 URL | zod で検証してそのまま保存                               | シンプル。API 呼び出しは検索の 1 回だけ | クライアントが値を書き換えて送れる                                                                         |
| B       | ID のみ                       | ID で Google Books に再問い合わせして保存                | 常に正しい値。状態を持たない            | 登録ごとに API 呼び出し(遅い・利用回数が増える)。登録が Google Books に依存                                |
| C       | ID のみ                       | 検索時の結果をサーバー側に保持しておき、そこから取り出す | 再問い合わせなしで改ざんも防げる        | 保存場所が必要(Workers はリクエスト間でメモリを共有しない → KV や D1 の一時テーブル)。期限切れの扱いも必要 |

## 採用理由(A)

- 自分専用で Cloudflare Access に守られているため、「クライアントが値を書き換えられる」は実害がない
- C は状態管理が増えるわりに、得られるのは改ざん防止だけ → KISS に反する

## 学び

- 「クライアントから来た値を信用するか」は、**誰が使うか(信頼境界)** で判断が変わる
  - 不特定多数が使うなら B(サーバーで正しい値を取り直す)が基本
  - 自分専用・認証済みなら A で十分
- サーバーに状態を持たせる案(C)は、サーバーレス(Workers)では保存場所と期限切れ処理が必ず付いてくる
- 将来、正確さが必要になったら B に変えればよい(状態を持たずに済む)
